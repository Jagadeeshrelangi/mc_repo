## Sprint 1.7.2a — Fuel Booking Location Banner Stability (no Continue jump)

### 4. Continue button jumped when location detection completed
- **Root cause:** the Step-3 location status widget changed its **intrinsic height per state** — idle (bare ~40px button), loading (44px card), success (OverflowBar card), denied/error (multi-row card) — so when auto-detection completed the banner grew/shrunk and shoved the scroll content (and everything above the pinned bottom bar) up/down. The Continue bar itself was already pinned (end of the body `Column`, not the scaffold bottom); the jump was the banner's height, not the bar.
- **Fix — reserve one constant height and fade content only** (`fuel_booking_screen.dart`):
  - `_buildLocationStatus()` now renders a fixed `SizedBox(key: Key('location_status_area'), width: double.infinity, height: 108)` (const `_locationStatusHeight = 108`).
  - Inside it, an `AnimatedSwitcher` (180ms, fade-only: `switchInCurve: easeOut` / `switchOutCurve: easeIn`) with a custom Stack `layoutBuilder` crossfades between states — no `AnimatedSize`, so the box never animates in height.
  - Each state sits in a `KeyedSubtree(key: ValueKey(_locationStatus))`; a `switch` expression dispatches to `_buildLocationLoading` / `_buildLocationSuccess` / `_buildLocationIdle` / `_buildLocationError`. All state texts are `maxLines: 1` + ellipsis so nothing wraps inside the reserved box.
  - The state content is wrapped in `LayoutBuilder → OverflowBox(alignment: topCenter, maxHeight: double.infinity)` so the real-world (Roboto) content (~90px max) fits naturally inside 108 while the Ahem test font's taller error card (~149px, buttons wrap to 2 rows at 320dp) is clipped by the Stack's `Clip.hardEdge` instead of throwing a `RenderFlex` overflow.
- **Regression proof:** the reserved area reports a **constant 108.0px height across all 5 states × 320/360/412dp × text scale 1.0/1.3**, Continue stays pinned (y=650 at 1.0, y=644 at 1.3), and zero overflow exceptions are thrown.

## Sprint 1.7.2b — Fuel Booking Step 3: one source of truth (state divergence on GPS success)

### 5. After GPS success, fields / preview / banner could render inconsistently until the route was reopened
- **Root cause:** Step 3 kept **two sources of truth**. The route-local state (`_addressController`, `_pincodeController`, `_locationStatus`, `_isDetectingLocation`) was seeded **only from detection** (`_applyLocation`), while the committed location lived in the **app-wide singleton** `FuelProvider.deliveryLocation`. So the very first render after GPS success could show: fields still empty/stale (controllers not yet populated), a **stale or missing preview** (`_buildLocationCard` rendered the *old* `deliveryLocation` — the old `_applyLocation` committed address fields + banner + submit together but left the preview reading the previous model), and a wrong/missing banner. Reopening the route masked it: the (now-populated) provider model was used on re-entry, so the state looked "fixed" by back → reopen. Also, a detection that reported success with **no readable address** previously rendered a green "success" banner next to **empty fields and a stale preview**.
- **Fix — make the provider model the single source of truth (`fuel_booking_screen.dart` + `delivery_location.dart`):**
  - `DeliveryLocation` gained a `pincode` field (`this.pincode = ''`) so one model carries address + pincode + coords + label.
  - `FuelProvider.setDeliveryLocation()` is the **only** writer of `_deliveryLocation` (notifyListeners), and the preview (`_buildLocationStep`) reads it via `context.watch<FuelProvider>()`, so every commit re-renders the preview atomically.
  - `_applyLocation(details, fallback:)` now derives the address; if it is **null/empty it sets `_LocationStatus.error`** (never a success banner next to empty fields); otherwise it builds ONE `DeliveryLocation` (`label: 'Current Location'`, pincode from `details.pincode` or a `\b\d{6}\b` regex on the address), calls `provider.setDeliveryLocation(model)` — the atomic commit — then mirrors it into the controllers via the new `_syncControllersFrom(model)`.
  - `initState`'s post-frame callback: when `provider.deliveryLocation != null` it also seeds controllers via `_syncControllersFrom` and sets `_locationStatus = success`, so **reopening renders identically** (fields, banner, preview all from the same committed model) even before async re-detection finishes.
  - `_commitLocation` (manual edit) passes `pincode: _pincodeController.text.trim()` into the model.
- **Root-cause proof / why reopening "fixed" it:** a probe with a slow fake (permission → GPS → geocode async hops) reproduced the divergence — BEFORE: first visit `address="…560001"`, reopen `address=""` and `banner=0`; AFTER: first visit and reopen are byte-identical (`address="MG Road, Indiranagar…" preview=1 delivery=… banner=1`). Reopening never *fixed* the data — it just read the committed singleton on a fresh route; the bug was that the first render seeded local state from detection instead of from the already-committed model. Now there is exactly one source of truth.
- **Regression tests** (`test/fuel_module_test.dart`, +3): "GPS success writes one consistent Step 3 state" (field text == provider model == preview == banner), "reopening the booking screen renders the location identically" (fresh route, same singleton providers → identical fields/banner/preview), "geocode failure shows error + Retry, never success with empty fields" (error banner, no success banner, `deliveryLocation` stays null). All three **failed before the fix** (reopen address empty / banner gone; geofail showed success) and **pass after**.

## Sprint 1.7.2c — Fuel Booking Continue: floating SnackBar was swallowing taps on the bottom bar

### 6. After the 1.7.2b UI fix, Step 3's Continue "sometimes does nothing" (no advance, no error)
- **Root cause:** the bottom bar (Back + Continue) was rendered **inside the Scaffold `body` Column** (`fuel_booking_screen.dart`). `MaterialApp`'s default `SnackBarBehavior.fixed` makes every validation SnackBar float **on top of the `body`** — i.e. over the Continue bar. While a validation SnackBar was on screen, its `Material` absorbed further taps exactly where the Continue button sits, so the press was **swallowed** (button still visibly enabled, nothing happens). Reproduced deterministically: press Continue during location detection → `_nextStep` case 2 saw an empty address (detection in flight) → "Please enter your delivery address" snack → detection then completed → a second press at the same spot hit the floating snack, not the button (probe: `SECOND-CONTINUE onStep4=0`).
- **Fix — 2 minimal changes (`fuel_booking_screen.dart`):**
  1. Moved the bottom bar out of the `body` Column into the Scaffold's **`bottomNavigationBar` slot** — the Scaffold then always floats SnackBars **above** it. Zero visual change (same surface container, top border, SafeArea, height).
  2. Added a guard at the top of `_nextStep` case 2: `if (_locationStatus == _LocationStatus.loading) return;` — a press during detection is swallowed up front, so the false "Please enter your delivery address" snack (and its blocking tap-absorber) never appears. Detection fills the address momentarily; the next press continues.
- **Root-cause proof:** probes before the fix: happy path advanced, but a second Continue during/after the floating snack reproduced `onStep4=0` (press absorbed by snack hit-test target) and `continueRect=Rect.fromLTRB(401.8,550.0,514.6,570.0)` overlapped the snack's tappable area. After the fix: `EARLY-CONTINUE snack=0 onStep4=0` (no false snack while detecting), `AFTER-DETECT CONTINUE onStep4=1` (advances once detected), `AFTER-STATION-SELECT onStep5=1 snackStillUp=1` (a Step-4 "select a station" snack no longer blocks Continue → advances to Step 5 while the snack is still visible).
- **Regression tests** (`test/fuel_module_test.dart`, +2): "Continue during detection is swallowed, then works once detected" (no false address snack while GPS running, no premature advance, advances after detection), "floating validation snack does not block the Continue bar" (Step-4 snack appears, then Continue advances to Order Summary while the snack is still on screen). Both fail if the bottom bar is reverted into the `body` Column / the loading guard is removed.

## Final Fuel Booking UI Certification (zero overflow)

### 1. Vehicle cards — "BOTTOM OVERFLOWED BY 2.0 PIXELS" eliminated
- **Root cause:** `FuelVehicleCard` was rendered inside `SizedBox(height: 120) → ListView.separated(horizontal)` (`fuel_booking_screen.dart`). A horizontal `ListView` constrains every item **tight** to the viewport height (120px), and the card's `Column` used `mainAxisSize.max` (filling all 120px). With real Roboto line metrics the card content needs ~122px (icon 36 + gap 12 + name ~23.4 + gap 2 + reg-number ~18.7 + padding 28), so the fixed 120px box overflowed by ~2px on device. Widget tests passed because the Ahem test font has shorter line metrics (20/16px) — the classic fixed-height-vs-content mismatch.
- **Fix — make the card and list responsive (no hardcoded height):**
  - `fuel_vehicle_card.dart`: `Column` → `mainAxisSize: MainAxisSize.min` (card is now content-sized, never forced taller/shorter).
  - `fuel_booking_screen.dart` steps 1 & 2: replaced `SizedBox(height: …) → ListView.separated` with `SingleChildScrollView(scrollDirection: horizontal) → Row(...)` (+10px separators), so the horizontal strip **heights itself to the card content** and still scrolls horizontally. Applied to both the vehicle list (was 120px) and the fuel-type list (was 140px — same latent pattern).
  - Regression proof: cards now report `Size(150.0, ~116.0)` (content-sized, not 120.0), and card height **grows** with text scale (116 → ~124 at 1.3) instead of clipping.

## Critical Runtime Bug Fixed
**Fuel Home Quick Order stuck on "loading…" forever.**

- **Root cause:** `FuelHomeScreen` was a `StatelessWidget` with no `initState` and no auto-trigger of `loadHome()` on first open (`lib/features/fuel_delivery/screens/fuel_home_screen.dart`). The screen is pushed via `MaterialPageRoute` from `starting_screen/home.dart:381` and `home_screen.dart:247`, but `loadHome()` was only reachable through pull-to-refresh (`:37`), the error retry (`:89`), the empty retry (`:97`), and `fuel_booking_screen.dart:53`. So `FuelScreenState` stayed `initial` forever and the `AppLoading` spinner rendered indefinitely.
- **Fix 1 — resilient `loadHome()`** (`fuel_provider.dart`): `_fuelTypes = _repository.getFuelTypes()` is synchronous and cannot throw; vehicles + history are loaded as parallel independent futures (`vehiclesFuture = _loadOptional(_repository.getSavedVehicles)`, `historyFuture = _loadOptional(_repository.refreshHistory)`) — heterogeneous `Future.wait` cannot infer the element types (compile error), so the futures are started in parallel and awaited sequentially. Each call is wrapped in `_loadOptional<T>` with a 10s `.timeout` and returns `null` on failure (never throws). Final state: `ready` when fuel types exist, `empty` otherwise; API errors only set `_errorMessage`. **One failing API can no longer block the page.**
- **Fix 2 — auto-load** (`fuel_home_screen.dart`): converted to a `StatefulWidget`; `initState` postFrameCallback calls `loadHome()` when `state == initial || state == error`. This mirrors the existing correct pattern in `mechanic_home_screen.dart:28-34`.
- **Regression test** (`test/fuel_module_test.dart`): "auto-loads data on first open and leaves loading" — fresh provider shows `AppLoading`, after two 800ms pumps loading is gone with 2 "Coming Soon" cards and 3 `RecentOrderCard`s. **Before the fix this test fails; after the fix it passes.**
